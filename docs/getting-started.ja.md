# MAGA 完全初心者ガイド

[English](./getting-started.md) · [简体中文](./getting-started.zh-CN.md) · **日本語** · [한국어](./getting-started.ko.md) · [Español](./getting-started.es.md)

このガイドは、Codex もターミナルもコードレビューも初めてという前提で書かれています。最後まで進めると、ローカルプロジェクトに MAGA が入り、最初の確認可能な成果を依頼できます。

## 準備するもの

- Windows または macOS のコンピューター。
- Codex を利用できる ChatGPT アカウント。
- インターネット接続。
- 一文で説明できるプロダクトのアイデア。
- プロダクトを置く空のフォルダ。

開発ツールを自分で用意する必要はありません。Codex が Node.js や Git などを確認し、不足があれば理由を説明して承認を求めます。

## 1. Codex を初めて開く

1. [ChatGPT デスクトップアプリ](https://learn.chatgpt.com/docs/quickstart?setup=app)をインストールします。
2. アプリを開き、ChatGPT アカウントでログインします。
3. ChatGPT の選択メニューから **Codex** を選びます。

Codex が表示されない場合は、アカウントまたはワークスペースで Codex が利用可能か確認してください。このガイドではコマンドライン版は不要です。

## 2. プロダクト用のフォルダを作る

エクスプローラーまたは Finder で空のフォルダを作ります。`client-feedback` のような分かりやすい名前で十分です。

デスクトップアプリでローカルプロジェクトを作るか、そのフォルダをプロジェクトとして開きます。Codex に表示されるフォルダが正しいことを確認してください。無関係な個人ファイルを含む大きな上位フォルダは選ばないでください。

## 3. Codex に MAGA をインストールしてもらう

プロジェクトを準備するために開いた Codex タスクへ、次を貼り付けます。

> このプロジェクトに https://github.com/thevenomsnake/MAGA の MAGA プラグインを導入してください。不足している前提環境を確認して必要ならインストールし、このフォルダで MAGA を初期化または復元して動作を検証してください。そのうえで、このプロダクトの内容が分かる名前の Project Lead タスクを作成または再利用し、準備できたら正確なタスク名を教えてください。技術的な手順は自分で実行し、本当に承認が必要な場合だけ私に確認してください。完全に行き詰まらない限り、ターミナルへコマンドをコピーするよう求めないでください。

コマンドは Codex に任せ、あなたは承認内容だけを判断します。

### 承認の見方

| 承認に含まれるもの | 通常の意味 | 対応 |
| --- | --- | --- |
| 選択したプロジェクトフォルダ | プロダクトファイルの作成や更新 | パスが正しければ承認 |
| GitHub または MAGA リポジトリ | プラグインの取得 | 保存先がプロジェクトか Codex のプラグイン領域なら承認 |
| Node.js または Git | 不足する前提環境の導入 | 用途の説明を読んでから承認 |
| ブラウザでのログイン | アカウント認証 | ブラウザでログインし、パスワードやトークンをタスクに貼らない |
| 無関係なフォルダ、支払い、不可逆な削除 | セットアップ範囲外 | いったん拒否し、必要な理由を質問 |

GitHub へのログイン、アカウントやリポジトリ設定、push、Issue や Pull Request への書き込みは、既定のセットアップ権限に含まれません。この依頼が前提とする GitHub 操作は、指定された MAGA リポジトリの取得だけです。

分からない場合は、こう返します。

> この承認で何がどこに変更されるのか、元に戻せるのかを、プロダクトの言葉で説明してください。

## 4. Project Lead タスクへ入る

セットアップが終わると、Codex は作成または再利用した Project Lead タスクの正確な名前を伝えます。同じプロジェクト内でその **Project Lead タスク**を開いてください。別の汎用タスクを作る必要はありません。そこでプロダクトを説明し、以後の判断を続けます。

### 任意：責務ごとのモデルを選ぶ

MAGA のプラグイン詳細ページで **Configure** starter prompt を選び、現在の利用枠に合う開始構成を選びます。MAGA のタスクが始まり、タスク内に設定パネルが開きます。

| 責務 | Pro · 品質優先 | Plus · 通常利用 | Free / Go · 使用量節約 |
| --- | --- | --- | --- |
| Project Lead | Sol · xhigh | Sol · xhigh | Terra · xhigh |
| 調査 | Sol · max | Sol · max | Terra · max |
| プロトタイプ | Sol · xhigh | Terra · high | Terra · high |
| デリバリー | Terra · xhigh | Luna · max | Luna · max |
| 診断 | Sol · max | Terra · xhigh | Terra · high |
| レビュー | Sol · xhigh | Sol · high | Terra · high |
| リリース | Sol · xhigh | Sol · high | Sol · high |

Business、Enterprise、Edu は Plus から始め、利用枠とポリシーが許す場合に Pro を選べます。API key 利用者は token 予算で選択してください。Sol は曖昧さと品質判断、Terra は日常作業、Luna は完了条件が明確なデリバリーでのみ **max** を推奨します。

最初の **Save** で設定を有効にし、7 つの責務を一つの完全な設定として固定します。保存先は現在の Codex Home であり、このプロダクトフォルダや Git 履歴ではありません。設定が適用されるのは、その後にあなたが明示的に作成を承認した新しいタスクだけで、既存タスクは変わりません。Project Lead も新しく作る場合にだけ適用されます。既存の Project Lead に新設定を使わせるには、「新しい設定で引き継いで」と明示し、代替タスクの作成を承認します。

MAGA は必要な責務と設定を自動で判断しますが、新しい Codex タスクを作る前にはプロダクトの言葉で同意を求めます。名前を付けた複数タスクは一度に承認できます。設定パネルの独立した `model/list` は参考用であり、タスクを実行する対象ホストの最終的な基準ではありません。MAGA は保存された `model` と `thinking` を新しいタスクの対象ホストへ渡して最終確認します。対象ホストが拒否した場合に限り、overrides を省いて一度だけ再試行し、ホスト既定値を使ったことを明示します。リクエストが「難しそう」という理由だけで設定を上げることもありません。

## 5. 最初のプロダクトを説明する

Project Lead タスク内では、一文から始められます。別のプロダクト説明例として、次のように伝えられます。

> MAGA を Project Lead として使ってください。フリーランスのデザイナーが顧客フィードバックを整理できるツールを作りたいです。コードは分からないので、プロダクトの言葉だけで質問し、私が直接確認できる動く成果を見せてください。

もう少し分かっている場合は、次を使います。

> MAGA を Project Lead として使ってください。**[対象ユーザー]** のために **[作るもの]** を作りたいです。現在の問題は **[問題]** です。最初の有用な成果では **[確認できる行動]** ができる必要があります。妥協できない条件は **[制約]** です。コードは分かりません。方向、リスク、権限境界を変える質問だけをしてください。

分からない項目があっても構いません。MAGA は答えを一緒に見つけるためのものです。

## 6. エンジニアリングではなくプロダクトの質問に答える

| 質問 | 意味 | 回答例 |
| --- | --- | --- |
| ユーザー | 誰が困っているか | 3〜10 社を担当するフリーランスデザイナー |
| 問題 | 今いちばん難しいこと | フィードバックがチャット、メール、文書に散らばる |
| 最初の有用な成果 | 最初に確認したい行動 | 案件にフィードバックを追加し、納品阻害を確認する |
| 制約 | 犠牲にできないこと | 説明なしでも画面を理解できること |
| 取捨選択 | 後回しにできること | チーム権限は後でよいが、案件別整理は必要 |
| 権限 | 今 Codex がしてよいこと | ローカル試作は可。公開や外部連絡は不可 |

分からなければ、「まだ分かりません。判断に役立つ最小の例を見せてください」と答えられます。

## 7. コードを見ずに受け入れ判断をする

動く成果が返ったら、次を確認します。

1. 対象ユーザーが主要な作業を完了できるか。
2. 最初の価値がすぐ見えるか。
3. 技術用語ではなくユーザーの言葉になっているか。
4. 空、誤り、欠落があるときにどうなるか。
5. 予想より遅い、分かりにくい、不安な箇所はどこか。
6. 技術を見せるだけでなく、実際の問題を解いているか。

観察したことをそのまま伝えます。

> フィードバックは追加できますが、まだ一般的なタスク管理に見えます。最初に案件の変化と納品阻害が見えることを期待していました。データは残し、情報の優先順位を変え、機能を増やす前に修正した流れを見せてください。

受け入れる場合は明示します。

> このプロダクトの範囲を受け入れます。受け入れた内容、未決事項、次の最小成果を記録してください。境界を示し、私が確認するまで次を始めないでください。

## 8. 翌日以降に続ける

同じプロジェクトで同じ Project Lead タスクを開き、次のように伝えます。

> 保存済みの状態からこの MAGA プロジェクトを続けてください。受け入れ済みの判断、未決事項、現在の動作、次に提案する成果を先にまとめてください。私が確認するまで変更しないでください。

同じプロダクトとファイルでは、同じ Project Lead タスクを使います。明確に分けられる成果には MAGA が別タスクを提案し、作成前にあなたの承認を求めます。

## 9. よくある問題

| 問題 | 対応 |
| --- | --- |
| ターミナル操作を求められた | 「その手順は自分で実行し、必要なら最小の承認を説明してください」 |
| 前提環境がない | Codex に導入、バージョン確認、中断箇所の再試行を依頼 |
| MAGA が認識されない | セットアップ用タスクへ戻り、インストールの検証と Project Lead タスクの特定を依頼 |
| GitHub から取得できない | 接続と GitHub へのアクセスを確認し、失敗した取得だけ再試行 |
| インストールに失敗した | エラー全文を渡し、診断、修復、検証まで Codex に依頼 |
| 質問が多すぎる | 「方向、リスク、権限境界を変える質問だけにしてください」 |
| 技術的には動くがプロダクトが違う | 観察結果、期待、重要なユーザー成果を伝える |
| Project Lead タスクがプロジェクトを忘れているように見える | 同じローカルプロジェクトか確認し、保存状態を先に読むよう依頼 |

## 10. 最低限の用語

- **プロジェクト：** 一つのプロダクトのフォルダ、タスク、永続的な文脈。
- **タスク：** プロジェクト内で見える Codex の作業単位。MAGA は名前付きの Project Lead タスクをプロダクトの主な入口として維持します。
- **プラグイン：** Codex に再利用可能な手順やツールを追加するインストール可能な束。
- **Project Lead：** MAGA のプロダクト向け調整役。
- **承認：** ダウンロードやファイル変更など、具体的な行動への許可。
- **受け入れ：** 動く成果が目的を十分に満たすというプロダクト判断。

## 11. MAGA から卒業する

ユーザー、問題、成果、制約を説明し、最小の証拠を求め、動作からフィードバックし、権限境界を判断できるようになれば、Codex を直接使う準備ができています。

MAGA を削除するには、**Plugins** を開き、**Installed** の MAGA から **Uninstall plugin** を選び、新しいタスクを開始します。プロダクトファイルは削除されません。

プロジェクト内の MAGA 専用ガイダンスも整理したい場合：

> このプロジェクトを MAGA から卒業させます。MAGA 専用のファイルや指示をすべて特定し、削除すると何が使えなくなるか説明し、正確な整理リストを見せてください。私が承認するまで削除しないでください。プロダクトファイル、判断、動くソフトウェアはすべて残してください。

MAGA が不要になることが、望ましい成果です。

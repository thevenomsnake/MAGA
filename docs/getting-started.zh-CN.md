# MAGA 完整新手指引

[English](./getting-started.md) · **简体中文** · [日本語](./getting-started.ja.md) · [한국어](./getting-started.ko.md) · [Español](./getting-started.es.md)

这份指引假设你从来没有用过 Codex、没有打开过终端，也不会 review 代码。完成后，你会在一个本地项目里装好 MAGA，并提出第一个可以直接验收的产品结果。

## 你需要准备什么

- 一台 Windows 或 macOS 电脑。
- 一个能够使用 Codex 的 ChatGPT 账号。
- 网络连接。
- 一个产品想法，一句话就够。
- 一个用来存放产品的空文件夹。

你**不需要**自己安装开发工具。Codex 可以检查 Node.js、Git 等必要环境，解释缺少什么，并在安装前请求你的授权。

## 1. 第一次打开 Codex

1. 安装 [ChatGPT 桌面客户端](https://learn.chatgpt.com/docs/quickstart?setup=app)。
2. 打开客户端，用 ChatGPT 账号登录。
3. 在 ChatGPT 选择器中选择 **Codex**。

如果没有看到 Codex，请先确认你的账号或工作区拥有 Codex 使用权限。这份指引不需要命令行版本。

## 2. 给产品准备一个文件夹

在文件资源管理器或 Finder 中新建一个空文件夹。可以使用简单的产品名，例如 `client-feedback` 或 `weekly-planning`；以后还可以修改。

在桌面客户端中建立本地项目，或者把这个文件夹作为项目打开。确认 Codex 显示的正是刚才创建的文件夹。Codex 可以读写挂载到项目的文件夹，因此不要选择包含大量无关私人文件的上级目录。

## 3. 让 Codex 安装 MAGA

把下面这段话粘贴到第一个 Codex 聊天：

> 请帮我为这个项目安装并配置 MAGA 插件：https://github.com/thevenomsnake/MAGA 。检查并安装缺少的必要环境，在当前文件夹初始化 MAGA，验证安装结果，然后告诉我什么时候需要新建聊天。技术步骤请由你完成，只在确实需要授权时让我确认。除非已经确实无法继续，不要让我把命令复制到终端。

Codex 应该自行检查环境、获取 MAGA、初始化项目并验证结果。命令由 Codex 选择；你只需要判断授权是否合理。

### 怎么判断一条授权请求

只有当请求明确符合 Codex 刚刚解释的步骤时才同意。

| 请求里出现 | 通常意味着 | 你怎么做 |
| --- | --- | --- |
| 你选择的项目文件夹 | 创建或修改产品文件 | 路径正确就可以同意 |
| GitHub 或 MAGA 仓库 | 下载插件 | 目标是当前项目或 Codex 插件目录时可以同意 |
| Node.js 或 Git | 安装缺少的必要环境 | 让 Codex 先说明用途，再决定是否同意 |
| 浏览器登录 | 验证某个账号 | 在浏览器里登录；不要把密码或访问令牌发到聊天中 |
| 无关文件夹、账号、付款或不可恢复删除 | 超出了安装范围 | 先拒绝，让 Codex 说明为什么需要 |

如果看不懂授权文字，直接回复：

> 请用产品语言说明这次授权会修改什么、修改在哪里、是否可以撤销。

## 4. 新建一个聊天

已安装的插件能力会在新聊天中生效。Codex 确认安装完成后：

1. 留在同一个项目里。
2. 新建一个 **Codex 聊天**。
3. 暂时保留安装聊天，后续出错时可以查完整错误信息。

### 可选：按职责选择模型

预填的 Balanced 推荐是很好的起点。打开 MAGA 插件详情页，选择 **Configure** starter prompt。Codex 会新建一个 MAGA 聊天，并在聊天中打开配置面板。这个面板不会嵌在插件详情页中，因为当前 Codex 插件页面还不支持任意自定义表单。

| 职责 | Balanced 推荐值 |
| --- | --- |
| Project Lead | Sol · medium |
| 研究 | Terra · medium |
| 原型 | Sol · medium |
| 交付 | Terra · medium |
| 诊断 | Sol · high |
| 审查 | Sol · high |
| 发布 | Sol · high |

**Sol** 适合模糊信息、综合判断和后果较重的决定；**Terra** 更快、更经济，适合边界清楚的工作；**Luna** 适合狭窄、重复的任务。思考深度中，**low** 适合机械任务，**medium** 是日常平衡，**high** 会为不确定性和风险投入更多推理。

在点击 **保存** 前，这些只是推荐，MAGA 使用 Codex 宿主默认值。第一次保存会把全部 7 个职责作为明确选择冻结在当前实例的 Codex Home，而不是产品文件夹或 Git 历史；之后只合并你改动的职责。保存的选择只用于你明确批准的新任务；已有任务不变，Project Lead 也只会在新建或你明确要求创建 replacement 接手时采用。面板的 `model/list` 只是参考目录；创建获批任务时，目标宿主会做最终验证。若目标宿主拒绝保存的选择，MAGA 才省略 overrides 重试一次，并告诉你使用了宿主默认值。

## 5. 描述第一个产品

一句话就能开始：

> 请让 MAGA 担任我的 Project Lead。我想做一个帮助独立设计师整理客户反馈的工具。我不懂代码，请只用产品语言提问，并给我可以直接检查的运行结果。

如果已经想得比较清楚，可以复制这个结构：

> 请让 MAGA 担任我的 Project Lead。我想为 **[哪类人]** 制作 **[什么产品]**。他们现在遇到的主要问题是 **[问题]**。第一个有用的结果应该让他们能够 **[可观察的结果]**。不能牺牲的要求是 **[约束]**。我不懂代码；只询问会改变产品方向、风险或授权边界的问题。

有些空格还不知道也没有关系。MAGA 应该帮助你发现答案，而不是要求你先写完需求文档。

## 6. 回答产品问题，而不是工程问题

MAGA 在开始构建前可能会问少量问题。知道多少就回答多少。

| MAGA 问什么 | 实际含义 | 回答示例 |
| --- | --- | --- |
| 用户 | 谁正在经历这个问题 | 同时服务 3–10 个客户的独立设计师 |
| 问题 | 现在什么最困难 | 反馈散落在聊天、邮件和文档里 |
| 第一个有用结果 | 最早值得检查的行为 | 把反馈放进项目，并看到什么正在阻塞交付 |
| 约束 | 什么不能被牺牲 | 设计师不看教程也能理解页面 |
| 取舍 | 什么可以以后再做 | 团队权限可以晚点做，按项目整理不能晚 |
| 授权 | Codex 现在可以做什么 | 可以做本地原型，但不能发布或联系任何人 |

你随时可以回答：“我现在还不知道。先给我看一个最小示例，帮助我做决定。”

## 7. 不看代码也能验收产品

Codex 返回可运行结果后，除非你自己想看，否则可以忽略代码 diff。用行为和体验检查产品：

1. 目标用户能不能完成最关键的任务？
2. 第一个有用价值是否很快就能看到？
3. 页面使用的是用户语言，还是内部技术术语？
4. 信息为空、错误或缺失时会发生什么？
5. 哪一步比预期更慢、更难懂或更不可信？
6. 它真的解决了产品问题，还是只展示了技术？

用观察结果反馈：

> 我可以添加反馈，但现在仍然像一个普通任务管理器。我期待最先看到的是项目变化和交付阻塞。保留底层数据，调整信息层级，在增加更多功能前先让我看修改后的流程。

不需要说出组件名、框架名、数据库或代码行。

这一小段产品达到要求后，明确告诉 MAGA：

> 我验收这一段产品结果。请记录已经接受的内容、仍然开放的问题，以及下一个最小有用结果。先把边界展示给我，在我确认前不要开始下一段。

## 8. 明天或新聊天中继续

打开同一个项目，新建 Codex 聊天，然后说：

> 请从已保存状态继续这个 MAGA 项目。先总结已经接受的决定、开放问题、当前产品行为和建议的下一个结果。在我确认总结前不要修改任何内容。

MAGA 把持久决定保存在项目里，因此你不需要依赖一条无限变长的聊天记录。不同结果可以用不同聊天；只要还是同一个产品和同一组文件，就继续使用同一个项目。

## 9. 常见问题

| 问题 | 你可以怎么说或怎么做 |
| --- | --- |
| Codex 让你运行终端命令 | “请你直接执行。如果需要更多权限，请说明最小必要授权。” |
| 缺少必要环境 | 让 Codex 安装、验证版本，然后只重试中断的步骤 |
| MAGA 没有被识别 | 确认安装已完成，然后新建聊天；插件能力会载入新聊天 |
| 无法从 GitHub 下载 | 检查网络和 GitHub 访问，再让 Codex 只重试失败的下载 |
| 安装失败 | 把完整错误发回 Codex，让它诊断、修复并验证，不要只给你命令 |
| Codex 问题太多 | “只问会改变方向、风险或授权边界的问题，其他部分使用可撤销默认值。” |
| 技术看起来厉害，但产品不对 | 说明你看到了什么、原本期待什么，以及真正重要的用户结果 |
| 新聊天像是忘了项目 | 确认聊天位于同一个本地项目，再让它先读取保存的项目状态 |
| 授权范围超过项目文件夹 | 拒绝，并要求只在项目范围内解决 |

## 10. 几个必须知道的词

- **项目（Project）：** 一个产品对应的文件夹、聊天和持久上下文。
- **聊天（Chat）：** 项目中一次目标明确的对话。
- **插件（Plugin）：** 为 Codex 增加可复用工作流和工具的可安装包。
- **Project Lead：** MAGA 中面向产品的协调角色，负责选择下一种有用实践并维护项目状态。
- **授权（Approval）：** 你允许 Codex 执行一项具体动作，例如下载环境或写入文件。
- **验收（Acceptance）：** 你判断一段可运行产品已经足够解决预期问题，可以被保留下来。

## 11. 从 MAGA 毕业

MAGA 是过渡坡道，不是永久中间层。当你能做到下面这些事，就可以尝试直接使用 Codex：

- 描述用户、问题、预期结果和不能牺牲的约束。
- 要求最小的证据来降低不确定性。
- 区分产品验收和工程验证。
- 根据观察到的产品行为反馈，而不是指挥实现方式。
- 判断哪些动作可以撤销，哪些必须明确授权。
- 从持久的产品决定继续工作，而不是依赖一段聊天记录。

要卸载 MAGA，请打开 **Plugins**，在 **Installed** 中找到 MAGA，选择 **Uninstall plugin**，然后新建聊天。卸载插件不会删除产品文件。

如果还想清理项目内 MAGA 专用的说明，可以让 Codex 执行：

> 我要让这个项目从 MAGA 毕业。请先找出所有 MAGA 专用的项目文件或说明，解释删除后哪些能力会停止工作，并列出准确的清理清单。在我批准清单前不要删除任何东西。必须保留所有产品文件、产品决定和可运行软件。

越来越少地需要 MAGA，正是我们希望出现的结果。

# MAGA 완전 초보자 가이드

[English](./getting-started.md) · [简体中文](./getting-started.zh-CN.md) · [日本語](./getting-started.ja.md) · **한국어** · [Español](./getting-started.es.md)

이 가이드는 Codex, 터미널, 코드 리뷰를 한 번도 사용하지 않았다고 가정합니다. 끝까지 진행하면 로컬 프로젝트에 MAGA가 설치되고 첫 번째로 확인 가능한 제품 결과를 요청할 수 있습니다.

## 준비물

- Windows 또는 macOS 컴퓨터.
- Codex를 사용할 수 있는 ChatGPT 계정.
- 인터넷 연결.
- 한 문장으로 설명할 수 있는 제품 아이디어.
- 제품을 둘 빈 폴더.

개발 도구를 직접 설치할 필요는 없습니다. Codex가 Node.js, Git 등 필수 환경을 확인하고 빠진 항목의 이유를 설명한 뒤 승인을 요청할 수 있습니다.

## 1. 처음 Codex 열기

1. [ChatGPT 데스크톱 앱](https://learn.chatgpt.com/docs/quickstart?setup=app)을 설치합니다.
2. 앱을 열고 ChatGPT 계정으로 로그인합니다.
3. ChatGPT 선택 메뉴에서 **Codex** 를 고릅니다.

Codex가 보이지 않으면 계정 또는 워크스페이스에 Codex 권한이 있는지 확인하세요. 이 가이드에서는 명령줄 버전이 필요하지 않습니다.

## 2. 제품 폴더 만들기

파일 탐색기나 Finder에서 빈 폴더를 만듭니다. `client-feedback`처럼 평범한 이름이면 충분합니다.

데스크톱 앱에서 로컬 프로젝트를 만들거나 그 폴더를 프로젝트로 엽니다. Codex에 표시된 폴더가 방금 만든 폴더인지 확인하세요. 관련 없는 개인 파일이 많이 들어 있는 상위 폴더는 선택하지 마세요.

## 3. Codex에게 MAGA 설치 요청하기

프로젝트를 준비하려고 연 Codex 작업에 아래 문장을 붙여 넣습니다.

> 이 프로젝트에 https://github.com/thevenomsnake/MAGA 의 MAGA 플러그인을 설정해 주세요. 빠진 필수 환경을 확인해 필요하면 설치하고, 이 폴더에서 MAGA를 초기화하거나 복구한 다음 정상 작동을 검증하세요. 이어서 이 제품을 알아볼 수 있는 이름의 Project Lead 작업을 만들거나 재사용하고, 준비되면 정확한 작업 이름을 알려 주세요. 기술 단계는 직접 수행하고 실제 승인이 필요할 때만 저에게 확인하세요. 정말 막힌 경우가 아니면 터미널에 명령을 복사하라고 하지 마세요.

명령 선택은 Codex에 맡기고, 사용자는 승인 요청만 판단합니다.

### 승인 요청 판단하기

| 요청에 포함된 내용 | 보통 의미 | 대응 |
| --- | --- | --- |
| 선택한 프로젝트 폴더 | 제품 파일 생성 또는 수정 | 경로가 맞으면 승인 |
| GitHub 또는 MAGA 저장소 | 플러그인 다운로드 | 대상이 프로젝트나 Codex 플러그인 영역이면 승인 |
| Node.js 또는 Git | 빠진 필수 환경 설치 | 용도 설명을 읽고 승인 |
| 브라우저 로그인 | 계정 인증 | 브라우저에서 로그인하고 비밀번호나 토큰을 작업에 붙이지 않기 |
| 관련 없는 폴더, 결제, 되돌릴 수 없는 삭제 | 설정 범위 밖 작업 | 거절하고 이유를 질문 |

GitHub 로그인, 계정이나 저장소 설정, push, Issue 또는 Pull Request 작성은 기본 설정 권한에 포함되지 않습니다. 이 설정 요청이 전제하는 GitHub 작업은 지정된 MAGA 저장소를 다운로드하는 것뿐입니다.

내용이 어렵다면 이렇게 답하세요.

> 이 승인이 무엇을 어디에서 바꾸는지, 되돌릴 수 있는지 제품 언어로 설명해 주세요.

## 4. Project Lead 작업으로 들어가기

설정이 끝나면 Codex가 만들거나 재사용한 Project Lead 작업의 정확한 이름을 알려 줍니다. 같은 프로젝트에서 그 **Project Lead 작업**을 여세요. 별도의 일반 작업을 만들 필요는 없습니다. 그곳에서 제품을 설명하고 이후의 결정을 이어갑니다.

### 선택 사항: 책임별 모델 고르기

MAGA 플러그인 상세 페이지에서 **Configure** starter prompt를 선택하고 현재 사용량에 맞는 시작 구성을 고르세요. MAGA 작업이 시작되고 작업 안에서 설정 패널이 열립니다.

| 책임 | Pro · 품질 우선 | Plus · 일반 사용 | Free / Go · 사용량 절약 |
| --- | --- | --- | --- |
| Project Lead | Sol · xhigh | Sol · xhigh | Terra · xhigh |
| 조사 | Sol · max | Sol · max | Terra · max |
| 프로토타입 | Sol · xhigh | Terra · high | Terra · high |
| 전달 | Terra · xhigh | Luna · max | Luna · max |
| 진단 | Sol · max | Terra · xhigh | Terra · high |
| 리뷰 | Sol · xhigh | Sol · high | Terra · high |
| 릴리스 | Sol · xhigh | Sol · high | Sol · high |

Business, Enterprise, Edu는 Plus로 시작한 뒤 사용량과 정책이 허용하면 Pro를 고를 수 있습니다. API key 사용자는 token 예산에 맞춰 선택하세요. Sol은 모호함과 품질 판단, Terra는 일상 작업, Luna는 완료 기준이 명확한 전달에만 **max**로 추천합니다.

처음 **Save**를 누르면 설정이 활성화되고 일곱 책임 전체가 하나의 완전한 설정으로 고정됩니다. 설정은 현재 Codex Home에 저장되며 이 제품 폴더나 Git 기록에는 들어가지 않습니다. 명시적 승인이나 프로젝트 Autonomy Policy가 적용되는 새 작업에만 사용되며 기존 작업은 바뀌지 않습니다. Project Lead도 새로 만들 때만 적용됩니다. 기존 Project Lead가 새 설정으로 이어받게 하려면 “새 설정으로 이어받아 줘”라고 명시하고 대체 작업 생성을 승인해야 합니다.

MAGA는 필요한 책임과 설정을 자동으로 판단합니다. 확인된 Autonomy Policy가 승인된 Ticket을 포함하면 해당 worker limit 안에서 이름 있는 작업을 만들 수 있습니다. 그렇지 않으면 새 Codex 작업 이름에 대한 동의를 요청합니다. 설정 패널의 독립적인 `model/list`는 참고용 목록일 뿐 작업을 실행할 대상 호스트의 최종 기준이 아닙니다. MAGA는 저장된 `model`과 `thinking`을 새 작업의 대상 호스트에 전달해 최종 검증합니다. 대상 호스트가 거부할 때만 overrides를 빼고 한 번 다시 시도하며, 호스트 기본값을 사용했다는 사실을 명확히 알립니다. 요청이 단지 “어려워 보인다”는 이유로 설정을 높이지도 않습니다.

## 5. 첫 제품 설명하기

Project Lead 작업 안에서는 한 문장으로 시작할 수 있습니다. 또 다른 제품 설명 예시는 다음과 같습니다.

> MAGA를 제 Project Lead로 사용해 주세요. 독립 디자이너가 고객 피드백을 정리할 수 있는 도구를 만들고 싶습니다. 저는 코드를 모르니 제품 언어로만 질문하고 제가 직접 확인할 수 있는 작동 결과를 보여 주세요.

더 알고 있다면 아래 구조를 사용하세요.

> MAGA를 제 Project Lead로 사용해 주세요. **[누구]** 를 위해 **[무엇]** 을 만들고 싶습니다. 지금 가장 큰 문제는 **[문제]** 입니다. 첫 번째 유용한 결과에서는 **[확인 가능한 행동]** 을 할 수 있어야 합니다. 포기할 수 없는 조건은 **[제약]** 입니다. 저는 코드를 모릅니다. 제품 방향, 위험, 권한 경계를 바꾸는 질문만 해 주세요.

모르는 항목이 있어도 괜찮습니다. MAGA가 답을 찾는 과정을 도와야 합니다.

## 6. 엔지니어링이 아니라 제품 질문에 답하기

| 질문 | 의미 | 예시 답변 |
| --- | --- | --- |
| 사용자 | 누가 문제를 겪는가 | 3–10개 고객을 관리하는 독립 디자이너 |
| 문제 | 지금 무엇이 어려운가 | 피드백이 채팅, 이메일, 문서에 흩어짐 |
| 첫 유용한 결과 | 가장 먼저 확인할 행동 | 프로젝트에 피드백을 추가하고 납품 방해 요소 확인 |
| 제약 | 포기할 수 없는 것 | 교육 없이 화면을 이해할 수 있어야 함 |
| 트레이드오프 | 나중으로 미룰 것 | 팀 권한은 나중에, 프로젝트별 정리는 지금 |
| 권한 | Codex가 지금 해도 되는 일 | 로컬 프로토타입은 가능, 게시나 외부 연락은 금지 |
| 작업 조율 | 승인된 작업 안에서 MAGA가 이름 있는 worker를 만들어도 되는지 | 가능, 상한은 먼저 2개로 설정. 새 범위와 외부 작업은 다시 확인 |

모르면 “아직 모르겠습니다. 판단에 도움이 될 가장 작은 예를 보여 주세요”라고 답할 수 있습니다.

## 7. 코드를 보지 않고 제품 승인하기

작동 결과가 나오면 다음을 확인하세요.

1. 대상 사용자가 핵심 작업을 끝낼 수 있는가?
2. 첫 가치가 빠르게 보이는가?
3. 기술 용어가 아니라 사용자 언어를 쓰는가?
4. 정보가 비어 있거나 잘못되거나 빠졌을 때 어떻게 되는가?
5. 예상보다 느리거나 불명확하거나 믿기 어려운 부분은 어디인가?
6. 기술만 보여 주는가, 실제 제품 문제를 해결하는가?

관찰한 내용을 그대로 말하세요.

> 피드백은 추가할 수 있지만 아직 일반적인 할 일 관리처럼 보입니다. 프로젝트 변화와 납품 방해 요소가 먼저 보여야 합니다. 데이터는 유지하고 정보 우선순위를 바꾼 뒤, 기능을 더 만들기 전에 수정된 흐름을 보여 주세요.

결과를 승인할 때는 명확히 말합니다.

> 이 제품 범위를 승인합니다. 승인한 내용, 열린 문제, 다음으로 가장 작은 유용한 결과를 기록하세요. 경계를 먼저 보여 주고 제가 확인하기 전에는 다음 작업을 시작하지 마세요.

## 8. 다음 날에도 계속하기

같은 프로젝트에서 같은 Project Lead 작업을 다시 열고 말합니다.

> 저장된 상태에서 이 MAGA 프로젝트를 계속해 주세요. 먼저 승인된 결정, 열린 질문, 현재 제품 동작, 제안하는 다음 결과를 요약하세요. 제가 확인하기 전에는 아무것도 바꾸지 마세요.

같은 제품과 파일에는 같은 Project Lead 작업을 사용하세요. 별도로 구분되는 결과에는 MAGA가 다른 작업을 제안하며, 만들기 전에 사용자의 승인을 요청합니다.

## 9. 자주 생기는 문제

| 문제 | 대응 |
| --- | --- |
| 터미널 명령을 실행하라고 함 | “그 단계는 직접 실행하고 필요한 최소 승인만 설명해 주세요” |
| 필수 환경이 없음 | Codex에게 설치, 버전 확인, 중단 단계 재시도를 요청 |
| MAGA를 인식하지 못함 | 설정 작업으로 돌아가 설치 검증과 Project Lead 작업 확인을 요청 |
| GitHub 다운로드 실패 | 인터넷과 GitHub 접근을 확인한 뒤 실패한 다운로드만 재시도 |
| 설치 실패 | 전체 오류를 Codex에 보내 진단, 복구, 검증까지 요청 |
| 질문이 너무 많음 | “방향, 위험, 권한 경계를 바꾸는 질문만 해 주세요” |
| 기술은 멋지지만 제품이 틀림 | 본 것, 기대한 것, 중요한 사용자 결과를 설명 |
| Project Lead 작업이 프로젝트를 잊은 것처럼 보임 | 같은 로컬 프로젝트인지 확인하고 저장 상태부터 읽게 함 |

## 10. 최소 용어

- **프로젝트:** 하나의 제품을 위한 폴더, 작업, 지속 컨텍스트.
- **작업:** 프로젝트 안에서 보이는 Codex 작업 단위. MAGA는 이름이 지정된 Project Lead 작업을 제품의 기본 진입점으로 유지합니다.
- **플러그인:** Codex에 재사용 가능한 워크플로와 도구를 더하는 설치 묶음.
- **Project Lead:** MAGA의 제품 중심 조율자.
- **승인:** 다운로드나 파일 수정 같은 구체적인 행동에 대한 허가.
- **제품 승인:** 작동 결과가 의도한 문제를 충분히 해결한다는 판단.

## 11. MAGA에서 졸업하기

사용자, 문제, 결과, 제약을 설명하고, 가장 작은 증거를 요청하고, 동작을 바탕으로 피드백하고, 권한 경계를 판단할 수 있다면 Codex를 직접 사용할 준비가 된 것입니다.

MAGA를 제거하려면 **Plugins** 를 열고 **Installed** 의 MAGA에서 **Uninstall plugin** 을 선택한 뒤 새 작업을 시작하세요. 제품 파일은 삭제되지 않습니다.

프로젝트 안의 MAGA 전용 안내도 정리하려면 Codex에 말하세요.

> 이 프로젝트를 MAGA에서 졸업시키겠습니다. 모든 MAGA 전용 파일과 지침을 먼저 찾고, 삭제하면 무엇이 중단되는지 설명한 뒤 정확한 정리 목록을 보여 주세요. 제가 승인하기 전에는 삭제하지 마세요. 모든 제품 파일, 제품 결정, 작동하는 소프트웨어를 보존하세요.

MAGA가 덜 필요해지는 것이 의도한 결과입니다.

# 多会话协作：用上下文隔离对抗注意力衰减

## 结论

> 不要把一个会话当作项目记忆。把仓库当作记忆，把会话当作有边界的注意力工作区。

多会话协作的核心收益不是“同时有更多 AI”，而是让每个会话只面对完成其职责所需的上下文。角色、事实和进度留在会话之外，新的会话才能以较低的信息噪声继续工作。

## 为什么长会话会失效

随着一个会话同时容纳探索、决策、实现、验证、发布和历史纠错，以下内容开始竞争有限的有效注意力：

- 当前目标与已经过期的目标；
- 全局约束与刚读到的局部实现细节；
- 用户决定与模型先前提出但未采用的方案；
- 不同模块的术语、权限和完成标准；
- 仍需执行的事实与仅供参考的历史过程。

结果通常表现为遗忘早期约束、重复研究、职责越界、把旧结论当成现状，或局部改动正确但项目方向错误。更长的提示和更完整的聊天记录只能延缓问题；它们也会继续增加需要竞争的上下文。

拆分会话的作用是**主动裁剪工作集**。它不增加模型的长期记忆，而是减少一次执行必须同时权衡的内容。

## 最小协作模型

几乎任何项目都可以从三个角色开始：

| 角色 | 关注内容 | 输出 |
| --- | --- | --- |
| 协调 | 目标、决策、优先级、任务边界 | 已提交的 Ticket |
| 执行 | 契约、所辖代码、直接依赖 | 实现、验证证据、提交 |
| 发布 | 精确版本、环境与回滚边界 | 发布结果 |

发布角色只在项目存在真实环境或不可逆操作时需要独立。研究、GUI、数据或工具角色也只在它们拥有显著不同的上下文或权限时再增加。

## 何时拆分

满足任一条件时，独立会话通常有价值：

1. 两项工作需要加载明显不同的文件、术语或历史。
2. 规划、实现、验收或发布需要相互制衡。
3. 某项工作具有独立权限或副作用边界。
4. 工作可以并行，而且文件所有权或 worktree 能真正隔离。
5. 当前会话已经积累大量过期路径，重新加载最小上下文比继续解释更便宜。

以下情况不要拆：任务很小、工作集相同、同一文件需要高频交替修改，或交接成本已经高于注意力节省。

## 协作协议

### 1. 固定角色，不固定会话

给角色定义职责、输入、输出和权限。会话 ID、本机路径和具体模型可以更换；角色名称、任务入口和完成规则必须能从仓库恢复。

### 2. 先提交 Ticket，再唤醒执行者

Ticket 至少写清：

- 目标和用户可观察结果；
- 允许修改的边界；
- 明确不做什么；
- 依赖与阻塞条件；
- 一次风险匹配的验证；
- 完成后需要回填的结果。

聊天消息只用于通知“去读取哪个版本的哪份契约”，不能承载独有需求。

### 3. 执行者只加载必要上下文

执行会话读取启动规则、当前 Ticket、所辖模块和直接依赖。不要默认加载全部历史、其他模块实现或完整聊天；缺少决策时返回协调角色，而不是自行扩大产品边界。

### 4. 状态必须可恢复

最小状态机是：

```text
open -> in_progress -> completed
                    -> blocked
```

完成记录至少包含实现摘要、验证事实和精确提交。阻塞记录必须说明缺少的决策、依赖或权限。任何新会话都应只靠仓库恢复当前状态。

### 5. 用隔离换取并行

共享同一工作树或同一批高冲突文件时，执行会话串行工作。只有独立 worktree、分支或明确文件所有权存在时才并行；“多个会话同时运行”本身不是有效并发。

### 6. 由协调角色收口

协调角色根据 Ticket 验收结果，处理跨模块依赖并集成提交。执行会话不把局部完成自动解释为项目完成，发布角色也不从模糊的“最新版”猜测目标版本。

## 最小仓库载体

工具和文件名可以变化，但需要覆盖四类持久事实：

- **启动规则**：新会话先读什么、禁止什么；
- **统一语言**：项目术语及容易混淆的概念；
- **Ticket**：目标、授权、边界、状态、验收和完成证据；
- **交接记录**：当前方向、已决定事项、未完成项和精确引用。

Git commit 提供版本身份和审计记录，worktree 提供写入隔离。两者都只是支撑注意力边界的工具，不是方法本身。

## 检查这套方法是否有效

不要用会话数量衡量。观察以下结果：

- 新会话能否不读取旧聊天就继续工作；
- 执行者是否很少重新询问已经决定的问题；
- 跨模块需求是否通过显式契约而非口头猜测传递；
- 并行工作是否很少产生未归属改动和 Git 冲突；
- 完成结论能否指向精确实现与一次充分的验证；
- 文档维护成本是否低于它减少的重复研究和返工。

如果交接文件不断增长，应拆成稳定知识与当前状态，归档过期过程，并让每个角色只加载与当前任务相关的索引。解决注意力衰减的系统本身也不能无限消耗注意力。

## 采用顺序

1. 先把重要事实从聊天迁入仓库。
2. 为下一项工作写一份 Ticket。
3. 只拆出一个执行会话，验证它能独立完成并回填结果。
4. 出现真实并发需求后再引入 worktree。
5. 出现真实权限或发布风险后再增加独立角色。

从一次可恢复的交接开始，不要先建立庞大的多代理组织图。

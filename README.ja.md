MAGA は、プロダクト職が Codex Desktop を使い始めるための橋渡しとなるプロダクト構築プラグインです。対象ユーザー、課題、体験、制約、トレードオフをプロダクトの言葉で説明すると、継続的に働く Project Lead が適切な手法を選び、調査、プロトタイプ、実装、検証、修復を調整しながら、その背景にある実践を見えるようにします。

コードを理解する必要も、Skills を選ぶ必要も、エンジニアリング用のセッションを管理する必要も、コードレビューを行う必要もありません。確認するのは、プロダクトの動作、体験、事業上の結果です。

> [!NOTE]
> MAGA はビジュアルな no-code ビルダーではありません。プロダクトにはコードがありますが、実装レイヤーは Codex が担当します。プロダクトの意図、優先順位、制約、受け入れ判断はあなたが保持します。

## はじめる

[Codex Desktop](https://openai.com/codex/)、Codex CLI、Node.js 18 以降、Git が必要です。Git リポジトリを初期化しない場合は `--no-git` を追加してください。

```bash
npx github:thevenomsnake/MAGA init ./my-product
```

新しいプロジェクトを開き、作りたいものをそのまま説明します。

```text
フリーランスのデザイナーが顧客フィードバックを整理できるツールを作りたい。
フィードバックは案件ごとに残し、納品を妨げている問題をすぐ確認できるようにしたい。
```

MAGA は最初に価値を確認できる成果を特定し、方向や権限の境界を変える質問だけを行い、必要な作業を開始します。アイデアを先に技術タスクへ変換する必要はありません。

既存環境にプラグインだけをインストールする場合：

```bash
npx github:thevenomsnake/MAGA install
```

初期化済みのプロジェクトと Project Lead を再開する場合：

```bash
npx github:thevenomsnake/MAGA start ./my-product
```

## Why MAGA

### なぜラッパーアプリではなく、プラグインなのか？

Codex はすでに難しいエンジニアリング作業を実行できます。リポジトリの理解、コードの作成と変更、チェックの実行、変更のレビュー、複数のプロジェクトチャットにまたがる作業、再利用可能な Skills の適用が可能です。OpenAI の公式ガイドも、Codex に永続的な文脈を与え、反復作業を Skills にし、安定した機能をプラグインとして配布する流れを説明しています。公式の [Codex ベストプラクティス](https://learn.chatgpt.com/guides/best-practices)、[Skills ドキュメント](https://learn.chatgpt.com/docs/build-skills)、[プラグインドキュメント](https://developers.openai.com/plugins/)を参照してください。

Codex という名前が示す通り、その中心はコードです。標準の用語と拡張モデルは、作業をエンジニアリング課題として表現し、技術的な成果を確認できる人ほど扱いやすく設計されています。

プロダクト職は「技術が分からず、指示するだけ」と言われがちです。それなら最後まで指示すればいい。MAGA は、プロダクトの目標と取捨選択をあなたが決め、コードを Codex に任せるためのプラグインです。

> **遠慮なく指示し、責任を持って受け入れる。**

あなたと Codex の間に、別のアプリケーションは必要ありません。モデルとクライアントの両方を作る会社は、両者を最も深く適合させられる立場にあります。Apple が自社のチップと OS を一体で最適化できるのと同じように、製品ロードマップ、機能の境界、インターフェース、リリース周期を一つにできます。Codex は今後も更新され続けます。独立したラッパーアプリは、新機能、操作方法、権限モデルを追い続けなければなりません。プラグインなら Codex の中に留まり、今不足しているプロダクト実践だけを追加し、不要になった時点でアンインストールできます。

MAGA は意図的に橋渡し用のプラグインとして設計されています。プロダクト職がすでに理解している言葉と判断から始め、成果の定義、証拠の収集、制約の設定、トレードオフの管理、動くソフトウェアの受け入れといった実践を徐々に見えるようにします。目指すのは永続的な依存ではなく、自立です。将来、Codex を直接使えるようになり、MAGA がほとんど、あるいはまったく必要なくなれば、このプラグインは役割を果たしたことになります。

MAGA が存在する理由は、モデルの能力とプロダクト協働が別の課題だからです。

一般的な Skill は、一つの反復作業を安定させます。しかし Skills を集めただけでは、次にどの作業を行うか、技術ワークフローをどう並べるか、各タスクにどの文脈が必要か、コード差分をどう評価するかを、利用者が理解している前提が残りやすくなります。

MAGA はその上に、次の運用モデルを追加します。

- プロダクト向けの Project Lead が、通常のプロダクト表現を受け取ります。
- 意図ベースのルーティングが、現在の証拠から Skills と手法を選びます。
- 永続的なプロジェクト状態が、判断、境界、役割、承認済み作業を保存します。
- Product Owner はコードレビューではなく、プロダクトの受け入れ判断を行います。

## 対象ユーザー

| あなたの立場 | 持ち込む重要な情報 | MAGA が担当すること |
| --- | --- | --- |
| 初めてソフトウェアを作る人 | 解決したい課題、対象ユーザー、基本的な期待 | 必要な確認と、確認可能な成果までの道筋 |
| プロダクトデザイナー | 体験基準、情報構造、インタラクションの取捨選択 | 調査、プロトタイプ、実装、検証の手法 |
| プロダクト責任者やマネージャー | 目標、優先順位、リスク、リソース、判断権限 | 文脈の維持、実行の調整、本当に判断が必要な事項の提示 |

プロダクトラインや部門横断チームをすでに率いている人ほど、MAGA を使いやすい場合があります。目標、優先順位、体験基準、リスク判断、権限の境界という最も重要な入力をすでに持っているからです。その役割にプログラミング能力を追加する必要はありません。

## 作業契約

| あなたが行う必要のないこと | あなたが引き続き決めること |
| --- | --- |
| コードを書く、読む、レビューする | 誰のどの課題をプロダクトが解決するか |
| 内部 Skills やエンジニアリング手順を選ぶ | 妥協できない体験と事業上の制約 |
| Tickets を分割し、タスクを命名し、セッションを管理する | 優先順位と許容できるトレードオフ |
| テストフレームワークや実装アーキテクチャを選ぶ | 動作する成果がプロダクト課題を解決しているか |

コードレビュー、テスト、デバッグ、技術検証は引き続き行われます。これらは Project Lead が管理するエンジニアリング上の証拠となり、Product Owner に別の専門職を要求しません。

## プロダクトを説明した後に起きること

1. **成果をそろえる。** MAGA がユーザー、課題、最初に観測できる価値、提供形態、重要な制約を特定します。
2. **次に必要な証拠を選ぶ。** Project Lead が、確認、調査、プロトタイプ、実装、検証、診断のどれが必要かを判断します。
3. **確認可能な最小単位を作る。** Codex が実装上の選択を担当し、実行、閲覧、検証できる成果を返します。
4. **エンジニアリングを確認する。** テスト、対象を絞ったレビュー、診断によって、技術的に成立しているかを確かめます。
5. **プロダクト判断へ戻る。** あなたが動作と体験を評価し、次の判断をプロダクトの言葉で伝えます。

たとえば：

```text
まだタスク管理ツールに見えます。まず今週何が変わったかを見せて、
そこから担当者をたどれるようにしたいです。
```

このフィードバックは情報設計と次の実装を変えます。コンポーネント名やコード行を指定する必要はありません。

## MAGA が記録するもの

1. **意図：** ユーザー、課題、期待する成果、制約。
2. **ルーティング：** 次が確認、調査、設計、実装、検証、修復のどれか。
3. **状態：** 確定した判断、未解決の質問、進行中の作業、次の有用な成果。
4. **権限：** 承認済みの操作と、新しい判断が必要な操作。
5. **証拠：** プロトタイプ、動作、テスト、診断、プロダクト受け入れ。

これらはプロジェクト内に保存されます。新しいチャットは、会話履歴をプロダクト記録として扱わず、永続状態から復元できます。

## プロダクトと権限の境界

MAGA は承認済みの作業を自律的に進めますが、一つの自然言語リクエストを無制限の権限には変えません。

- 指定されたプロジェクト内の可逆な変更と、リスクに応じたチェックは通常の実行です。
- 公開、支払い、アカウント操作、外部メッセージ、不可逆な削除には明示的な権限が必要です。
- 既存の判断から推論できないプロダクト上の取捨選択は Product Owner に返されます。
- UI は Codex Desktop のままで、MAGA は並行するダッシュボードを作りません。

## 構成

現在のリリースは **v0.9.0** です。15 個の登録済み Skills と、必要なときだけ読み込む内部手法ライブラリを含みます。

| レイヤー | 責任 |
| --- | --- |
| Project Lead | プロダクト表現を受け取り、状態を維持し、手法を選び、タスクを調整する |
| プロダクト発見 | 確認、調査、ドメイン言語、コンセプト、優先順位 |
| 設計とデリバリー | 計画、プロトタイプ、実装、検証、完了 |
| 診断と単純化 | デバッグ、コードレビュー、不要な複雑性の削減 |
| 手法ライブラリ | 上流ワークフローを必要時のみ読み込み、毎回の会話を圧迫しない |

実装を見る：[Skill catalog](./plugins/maga/skill-catalog.json) · [Project Lead](./plugins/maga/skills/project-lead/SKILL.md) · [プロダクト指向 Project Lead](./playbooks/product-oriented-project-lead.md)

<details>
<summary><strong>ルーティング、タスク、権限</strong></summary>

### ルーティング

Project Lead は最初に必要な証拠の種類を判断し、登録済み Skill または内部手法を選びます。Skill を明示的に呼び出すこともできますが、通常のプロダクト作業では必要ありません。

### タスク境界

作業は既定で現在のタスク内に残ります。並列作業、分離された文脈、独立した権限境界、独立した受け入れに適した具体的な対象がある場合にだけ別タスクを作ります。空の調査、プロトタイプ、実装、レビュー用タスクは事前作成しません。

### 権限

自然言語による承認は、明確に説明された現在のプロダクト単位に適用されます。将来の Tickets や大幅に拡張された成果へ自動的には広がりません。

詳細：[Capability routing](./plugins/maga/skills/project-lead/references/capability-routing.md) · [Native Codex loop](./plugins/maga/skills/project-lead/references/native-codex-loop.md) · [Project memory](./plugins/maga/skills/project-lead/references/project-memory.md)

</details>

<details>
<summary><strong>インストール時の動作</strong></summary>

`install` は MAGA marketplace を追加または更新し、`maga@maga` をインストールします。

`init` は空のディレクトリを受け取り、次を実行します。

1. プラグインをインストールする。
2. `.ai-workflow/PROJECT.md`、`AGENTS.md`、`.gitignore` を作成する。
3. Git を初期化し、ユーザー情報が設定済みなら最初のコミットを作成する。
4. 明確な名前の Project Lead タスクを作成または再利用する。
5. Codex Desktop でプロジェクトを開く。

`start` は既存のプロジェクト状態を読み、ファイルを書き換えずに Project Lead を復元します。全オプションは `npx github:thevenomsnake/MAGA --help` で確認できます。

</details>

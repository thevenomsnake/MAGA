## 如何阅读证据

本文严格区分三种陈述：

- **官方自述**：项目作者对目标、价值或设计原则的表述。这能证明项目如何定义自己，不能自动证明实际效果。
- **源码事实**：可由固定 commit 的文件、规则、控制流或测试直接验证的行为。
- **分析判断**：基于上述证据推导出的用途、局限和 AI 协作意义，不冒充项目作者的结论。

## 来源与版本边界

**官方自述。** 项目把自己定义为两个产物：一个展示常见 AI 视觉与文案套路及 before/after 示例的多语言网站，以及一个把这些条目转成扫描、解释和修复流程的 Agent Skill。见固定版本的 [仓库 README](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/README.md) 和 [Skill README](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/README.md)。

**源码事实。** `kill-ai-slop` 是 `yetone/kill-ai-slop` 的独立仓库，不是其他 Skills 合集的子目录。固定版本采用 [Apache-2.0](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/LICENSE) 许可。该版本的 [SKILL.md](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/SKILL.md)、[taxonomy](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/references/taxonomy.md) 和 [scanner](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/scripts/scan.mjs) 均包含 **35 个编号条目**。

**源码事实。** 同一 commit 的仓库根 README 仍称网站收录 33 类，而 Skill README、SKILL、taxonomy 和 scanner 都是 35 类。这是上游文档内部的不一致。本文以直接定义规则的 taxonomy 和 scanner 为准，并固定 commit，避免把动态数量写成永久规格。

## 项目要解决的问题

**官方自述。** 项目将 “AI slop” 描述为：产品堆叠大量样式和细节，却没有形成焦点；渐变、发光、吉祥物、emoji、卡片等默认动作同时出现，使不同产品看起来像同一模板。它反复强调，某种元素本身不是问题，**没有人选择和解释的默认动作**才是问题。[taxonomy](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/references/taxonomy.md)

官方 Skill 给出六条规范性原则：

1. 装饰前先做决定。
2. 一个强调色、一种声音。
3. 用尺度和空间建立层级。
4. 先做减法。
5. 具体文案胜过亢奋文案。
6. 装饰必须传递含义。

**分析判断。** 这不是一套普适审美定律，而是一份带明确品味立场的反模式目录。它真正可复用的部分，是把模糊的“看起来很 AI”拆成可命名、可定位、可讨论、可批准的候选，而不是证明某一套极简视觉天然更好。

## 35 类体系

以下名称和修复方向来自固定版本的 [taxonomy](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/references/taxonomy.md) 与 [fixes](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/references/fixes.md)，属于**官方自述的分类与处方**；它们是否适合具体产品仍需判断。

### 色彩（01-06）

1. **01 靛蓝到紫色渐变**：Tailwind 常见紫色渐变、紫色 glow；改为有理由的单一强调色，或有明确方向和用途的渐变。
2. **02 渐变标题字**：`background-clip:text` 加透明文字；改用实色，通过字号、字重和空间建立层级。
3. **03 暖色“温馨”套色**：浅 amber/stone/orange 与米色背景的默认组合；改为中性基底加一个克制暖色。
4. **04 默认语义彩虹**：info 蓝、tip 黄、success 绿、error 红的框架默认色并列；从项目色板派生少量必要状态色。
5. **05 单色状态框**：边框、文字和透明背景使用同一红/黄/绿；先用文字和字重表达状态，在中性表面上只保留必要颜色。
6. **06 作为气氛的渐变**：全页 radial glow、卡片表面渐变、按卡片强调色染色、重复条纹和有色阴影；改为稳定实色表面、细边线与克制阴影。

### 字体（07-12）

7. **07 单词级衬线斜体强调**：在无衬线标题里换一个衬线斜体词；改用同一字体的字重、位置或换行。
8. **08 不合场景的衬线字体**：工具或 SaaS 使用展示衬线做 UI、正文或巨大斜体 hero；工具界面改用经过选择的可读字体，真正编辑型产品可保留衬线。
9. **09 装饰性删除线与高亮**：删除线、下划线、mark 不承担删除、链接或批注语义；让结构承担强调。
10. **10 每个标题上方都有 kicker**：重复的全大写 FEATURES、HOW IT WORKS 等小标签；删除复述标题的 kicker，只保留新增类别、日期等信息的标签。
11. **11 整句超大标题**：十多个词全部使用 display size 和紧字距；把真正重要的少数词放大，其余信息移入正常字号副标题。
12. **12 扁平字号层级**：标题、正文和标签都挤在 14-18px；减少字号级数，但让相邻层级有真实差异。

### 文案（13-15）

13. **13 段落中散布高亮词**：多个词被着色或加粗；让句子结构表达重点，最多保留一个有意强调。
14. **14 AI 营销文案声线**：`not just X, it's Y`、`say goodbye to`、`supercharge`、三词短句、滥用破折号和 “X theater”；改写为可核对的名词、数字与后果。
15. **15 emoji 泛滥**：标题、按钮和列表项都以 emoji 装饰；删除装饰性 emoji，只保留真正传递状态的符号。

### 组件（16-25）

16. **16 发光状态点**：绿色圆点带 halo、pulse 或 glow，甚至为没有真实状态的营销文案假装 “Live”；改为平面圆点加文字，无状态则删除。
17. **17 圆角卡片加彩色左边框**：普通列表都包装成 callout，或用粗强调色边框让卡片 “pop”；让列表回归列表，把 callout 留给真正旁注。
18. **18 圆角方块图标砖**：每个功能都配一个淡色圆角图标块，或在卡片放巨大线性图标；没有信息价值的图标应删除。
19. **19 最大圆角与玻璃拟态**：卡片、输入框都 `rounded-full`，表面普遍透明模糊；统一较小圆角，用实色表面和空间建立深度。
20. **20 过大阴影**：小元素投射范围远大于自身的软阴影，或同时使用 hairline 与大阴影；收敛为少量真实 elevation，通常只留边线或阴影之一。
21. **21 不嵌套的圆角**：内外层使用相同大圆角；按 `inner = outer - padding` 计算，或不圆内层。
22. **22 到角落消失的边框**：外层负责圆角与裁剪，子层负责方形边框，导致圆角弧线被裁掉；让边框和圆角由同一元素拥有。
23. **23 badge 与 pill 泛滥**：New、Beta、Popular 等装饰标签到处出现；只保留真实状态或版本。
24. **24 粗糙 AI SVG 图标**：用圆形、方块等 primitive 拼出的占位吉祥物或品牌标记直接上线；改用真正设计并经过打磨的图标。
25. **25 图标放在同色浅底中**：蓝图标放浅蓝砖、绿图标放浅绿砖；让图标继承文字色，或使用经过选择的实色表面。

### 动效（26-27）

26. **26 弹跳 hover**：卡片和按钮普遍 `hover:scale`、位移、弹性 easing、`transition-all`；只动画真正变化的属性，使用短而标准的 easing。
27. **27 摇晃的 spinner**：旋转中心偏离，或 rotate keyframe 覆盖居中的 translate；分离定位与旋转，校准 SVG 画面中心，并观察完整一圈。

### 布局（28-32）

28. **28 全大写卡片网格**：CAPS 小标签加数字/图标被复制成等权卡片；找出最重要的信息并完整表达，不让所有内容等重。
29. **29 编造的统计数字行**：10k+、99.9%、24/7 被当作版式填充；只展示已测量并注明来源的真实数字。
30. **30 装饰性 01/02/03 章节号**：无顺序的营销段落被编号；只为安装步骤、目录、变更记录等真实序列编号。
31. **31 卡片嵌套卡片**：多层表面各自带边框、圆角、阴影和 padding；每个区域只保留一个主要表面，内部用对齐、间距和细线分组。
32. **32 所有关系使用同一间距**：`gap-4`、`space-y-4` 到处重复；相关内容靠近，不相关分组拉开。

### 演进套路（33-35）

33. **33 到处都是 Inter**：Inter、Space Grotesk、Geist、Manrope、Plus Jakarta Sans 被无理由地默认采用；比较候选字体并记录选择理由，最终仍选 Inter 也可以。
34. **34 “品味终端”**：全局等宽字体、近黑背景、单一暖色和 ASCII 装饰；等宽字回到代码，终端隐喻只用于真正相关的产品。
35. **35 “编辑型仪表盘”**：运营界面套用大号衬线问候、衬线数字、奶油纸张和 tracked caps；扫描型界面使用可读无衬线与 tabular lining numerals，编辑型表面才使用展示衬线。

**分析判断。** “Classic / Evolved” 是作者对流行套路阶段的分类，不是稳定标准。尤其 33-35 针对的是“默认采用且没有理由”，不能从字体名称、暗色背景或衬线字本身推出设计有问题。

## Scanner 实际做了什么

本节均为可从固定版本 [scan.mjs](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/scripts/scan.mjs) 直接验证的**源码事实**。

### 输入与遍历

- scanner 是无第三方依赖的 Node ESM 脚本，只读文件，不修改项目。
- 接受一个扫描根目录；根目录不存在或不是目录时返回非零状态。
- 扫描 `.html`、`.css`、`.scss`、`.sass`、`.less`、`.tsx`、`.jsx`、`.ts`、`.js`、`.mjs`、`.cjs`、`.vue`、`.svelte`、`.astro`、`.md`、`.mdx`、`.php`、`.twig` 与 `tailwind.config.*`。
- 跳过常见依赖、构建、缓存和版本控制目录，跳过 lockfile、`*.min.js/css`、超过 512 KiB 的文件，以及超过 2000 字符的命中行。
- scanner 会通过 realpath 排除自身 Skill 目录，避免扫描规则文档产生自命中。

### 匹配与输出

- 35 个条目各自包含正则数组、组名、显示名和一句修复方向。
- 正则针对整个文件运行，因此支持跨行模式；命中位置再映射回起始行。
- 同一个 tell 在同一行最多记录一次；JSON 不会反映该行有几个独立匹配。
- 人读输出按 tell 分组，每组最多展示 12 个位置；JSON 输出保留该组记录到的全部行级命中。
- `--json` 输出扫描文件数、命中组数、行级命中数和每组的 `id/group/name/fix/hits`。
- `--only`、`--skip` 按 id 缩小规则；`--exclude` 以项目相对路径的**子串**排除文件或目录。
- `deslop-ignore`、`deslop-ignore-next-line`、`deslop-ignore-file` 可抑制全部或指定 id，解析不是语言语法感知的，只要行内出现相应文本就可能生效。
- `--rules=file.mjs` 动态导入额外 JavaScript 规则模块。模块可导出 `default` 或 `tells` 数组；字符串 pattern 被编译为不区分大小写的 Unicode 正则。
- 人读输出会转义控制字符；JSON 由 `JSON.stringify` 序列化。

### Markdown 与文案范围

- scanner 只把 `.md` 视为纯 prose；该文件类型只运行标记了 `copy: true` 的 13、14、15、29。
- `.mdx` 被当作代码与标记的混合文件，因此运行全部规则。
- 14 的核心文案规则是英语短语。仓库提供 [俄语扩展示例](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/scripts/rules.ru.mjs)，但没有内置中文等语言规则。

### 源码与参考文档的细小差异

以下不是审美争论，而是固定版本可核对的覆盖差异：

- detection 的 24 号手工 `rg` 示例包含独立 `.svg` 文件，但 scanner 的扩展名集合不含 `.svg`；它只能在被扫描的 HTML/组件等文件里命中 inline SVG 或相关文件名字符串。
- detection 的 34 号手工 `rg` 示例包含 `.md`，但 scanner 不把 34 标成 `copy: true`，所以纯 Markdown 中的 ASCII/等宽终端风格不会由内置 scanner 的 34 号规则报告。
- detection 为 12、21、22、24、27、31、32 等条目明确要求视觉或结构确认；scanner 只能找到局部代码线索，不能验证完整条件。
- `--exclude` 是子串匹配，不是 glob；宽泛 token 可能排除比预期更多的路径。
- `--rules` 会执行 JavaScript 模块，而不是读取无执行能力的数据文件。

### 测试覆盖能证明什么

**源码事实。** [scan.test.mjs](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/scripts/scan.test.mjs) 测试了：非法根目录、控制字符转义、多行匹配、若干代表规则、排除 Skill 自身、PHP/Twig、抑制指令、`--only/--skip/--exclude` 和额外规则模块。

**分析判断。** 这些测试证明主要机制在构造样例上可工作，不证明 35 条全部有独立测试，也不证明真实项目中的精确率、召回率或修复后的视觉质量。

## 官方工作流

本节是 [SKILL.md](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/SKILL.md) 的**官方自述**，不是本文自行扩张的测试流程。

1. **Scope**：确认扫描哪个应用或网站源码。多应用项目先询问范围；默认排除依赖、构建物、锁文件和压缩文件。
2. **Scan**：运行 bundled scanner，得到按类别分组的 `file:line` 候选；把结果当地图，不当判决。
3. **Triage**：打开每个命中，结合品牌 token、logo、插画、产品语义和上下文判断是默认套路还是有意设计。
4. **Report**：修改前先汇总已确认命中、理由和拟议修复，并让用户选择批准哪些组。
5. **Fix**：以保留意图和功能的最小变更修复批准项；优先改共享 token/组件，不私自发明品牌色，文案改为具体表达而不是只删除。
6. **Close**：重跑 scanner 观察计数变化，说明刻意保留项；有运行环境时进行视觉检查，因为扫描通过不等于页面更好。

官方 guardrails 还要求尊重原作者、避免无关格式化、不使用 `git add -A`、不引入新依赖，并保持小而可审查的 diff。

**分析判断。** 真正的控制点是 `Triage → Report → 用户批准`。scanner 只拥有“提出候选”的权限，Skill 执行者才负责解释，用户保留价值判断权。若跳过这三步，整个工具会退化成用一套主观正则批量重写设计。

## 误报边界

### 官方明确承认的误报

**官方自述。** [detection](https://github.com/yetone/kill-ai-slop/blob/96d1ca568a1db7e1ef9a381644c744440f816ee4/skill/references/detection.md) 为大多数规则提供了 confirm 或 false-positive 条件，包括：

- 紫色本来就是品牌色，渐变属于 logo、插画或单个有意 hero。
- 暖色是食品、咖啡或手工品牌的身份。
- 衬线服务于出版、文化或编辑型产品。
- 删除线表示真实删除，下划线表示链接，mark 表示真实批注。
- kicker 增加了类别、日期或序列信息。
- emoji 来自代码示例、emoji 功能或用户生成内容。
- `rounded-full` 用于头像或真正的 pill。
- 状态颜色确实承载重要且会变化的状态。
- 大表面使用与尺寸相称的阴影。
- SVG 属于真实设计的 logo 或图标系统。
- 卡片子层是预览、embed 等独立对象。
- 数字有真实测量和来源，编号表达真实顺序。
- Inter 是比较后选择的字体，终端隐喻就是产品对象，衬线用于真正编辑型页面。

官方提交 [`d0512c9`](https://github.com/yetone/kill-ai-slop/commit/d0512c9fe54afce32ac0e6be7ffd217363180919) 还记录过一次自我纠正：旧的发光在线状态例子其实有可辩护语义，于是改成“没有真实状态却在营销 hero 中假装 Live”的版本。这直接支持“组合和语义才决定问题”的边界。

### 从源码可见的高召回模式

**源码事实。** 部分规则故意很宽：任意浅色 `amber/orange/stone`、`font-serif`、`rounded-full`、大圆角、`transition-all`、`grid-cols-3`、`font-mono`、常见字体名、emoji，或带特定 `<circle r>` 的 inline SVG 都可能成为候选。

**分析判断。** 这些规则适合找入口，不适合单独定罪。它们无法从局部文本证明“到处都是”“内外层嵌套错误”“数字是编的”“字体没有比较过”或“终端隐喻不服务产品”。越依赖频率、层级、语义和作者意图的条目，越不能自动化为硬门禁。

## 漏报与能力边界

**源码事实。** scanner 是正则驱动的静态文本扫描，因此只能看到列出的扩展名和文本形态。变量计算、运行时 class 拼接、CSS-in-JS 的非典型表达、生成后 DOM、未列出的文件类型、超大文件和超长行都可能绕过规则。内置非英语文案覆盖有限，部分条目只用一个很窄的代码信号。

**分析判断。** 它无法可靠判断：

- 渲染后的整体构图、视觉频率、响应式表现和真实内容密度；
- 动画是否顺滑，spinner 是否真正绕中心旋转；
- token 经过主题、变量、组件和条件分支后的最终样式；
- 品牌历史、用户预期、产品语义与作者选择过程；
- 信息架构、可用性、无障碍、性能和功能正确性；
- 文案中的事实是否真实，统计数字是否有外部来源。

上游扩展 taxonomy 时明确没有把行长、对比度、标题层级、图片损坏等所有通用质量问题都收入 AI-slop 分类，见提交 [`90a2522`](https://github.com/yetone/kill-ai-slop/commit/90a25223b39babb7cadc830ec178ac545bd9dc13)。所以它不能替代无障碍审查、UX 研究、功能测试、完整代码 review 或专业设计判断。

## 实际价值

以下均为基于一手证据的**分析判断**。

### 1. 把审美反馈变成可定位语言

“模板感”“太像 AI”很难执行。35 个名称、代码信号、误报说明和修复方向，使反馈能落到类别、位置和理由上。价值不在统一审美，而在让人和代理知道正在讨论哪个决定。

### 2. 用静态扫描压缩阅读范围

无依赖 scanner 能先把广阔前端源码压缩为少量分组候选，JSON 又可成为结构化交接物。它节省的是搜索注意力，不是替代设计注意力；仓库没有提供准确率或用户研究数据，不能宣传为已证明的质量提升。

### 3. 将判断与执行分权

先 triage、再 report、最后按组批准，使“发现一个模式”和“有权修改它”成为不同动作。相较于“把页面变高级”这类开放提示，这个流程更容易审查，也更能保护品牌和原作者意图。

### 4. 将保留决定持久化

类别级 `deslop-ignore` 能把已确认的有意选择留在源码附近，避免未来会话重复争论。优先使用指定 id 的抑制，比整行或整文件全部静默更能保留新问题的可见性。

### 5. 迫使修复落到共享决策

fixes 的顺序是 token/theme、共享组件、一次性调用点、文案。这个顺序鼓励代理先找系统性决定，再控制 diff，而不是逐个替换命中字符串。

### 6. 它自身证明“删除不等于设计”

官方提交 [`bf88108`](https://github.com/yetone/kill-ai-slop/commit/bf8810874d82ed08334e2b1c4b08e48a85fabed4) 记录：部分读者更喜欢 slop 版本，因为 clean 版本只删除装饰，没有把剩余结构做好；作者据此重做示例，并明确写下 “Deletion is not design”。这意味着 scanner 最多帮助移除无依据默认动作，不能自动补上产品声音、信息结构和视觉工艺。

## 适用与不适用

以下是综合官方范围与源码能力后的**分析判断**。

**适合：**

- 受支持 Web 技术栈中的 landing page、文档、管理界面和产品 UI；
- AI 原型生成后，第一次有边界的设计去默认化；
- 合并前针对新页面或新组件的定向视觉与文案审查；
- 已有品牌 token、内容目标或设计方向，可据此 triage；
- 团队需要共享词汇，并希望把修改拆成可批准的小组。

**不适合：**

- 把命中数当质量分数、绩效指标或 CI 硬门禁；
- 没有人工 triage 就自动批量修复；
- 用“零命中”替代视觉验收，或把所有产品收敛成同一种无装饰极简风；
- 原生移动端、游戏、强艺术表达、品牌实验等规则语境外产品，除非先建立专用 taxonomy 与检测器；
- 替代无障碍、功能、信息架构、转化、性能、安全或完整代码质量审查；
- 从不可信来源加载 `--rules` 模块，因为它会以 JavaScript 执行。

## 与注意力控制的关系

以下是本文面向 AI 协作的**分析判断**。

1. **知识外置**：taxonomy、detection、fixes、scanner 和 suppression 是持久上下文。新会话不用依赖一段越来越长的提示来重建 35 个概念。
2. **先压缩再理解**：scan 将全仓库压缩成分组候选；triage 只为当前类别加载相关文件、设计 token 与产品语义，减少无关信息竞争。
3. **认知阶段隔离**：发现、解释、批准、修改和视觉验收不是同一动作，避免代理从正则命中直接滑向大规模改写。
4. **价值判断留给人**：report 把用户批准范围变成任务契约；scanner 没有最终决定权。
5. **显式保存例外**：id-scoped suppression 记录“这是有意选择”，降低后续会话重复消耗注意力。
6. **用小闭环结束**：修改共享 token 或组件的最小范围，重扫真正变化的事实，再做一次针对性视觉验收；不追求抽象的零告警。

范围很大时，可以让一个注意力工作区完成扫描和分类，再把用户批准的少数组交给新的执行会话。交接物应是：固定规则版本、扫描范围、品牌约束、已确认命中、刻意保留项和批准组，而不是整段聊天。范围窄时无需分会话，一次短闭环更简单。

```text
固定 Skill 版本与页面范围
→ 加载品牌/产品约束
→ 扫描生成候选
→ 按组读取上下文并判断默认/有意
→ 报告并由用户批准
→ 修改共享决策的最小范围
→ 重扫变化 + 一次视觉验收
→ 记录刻意保留项
```

## 方法论结论

以下是从本项目自身结构提炼出的**分析判断**，不代表作者原话。

一个可执行的审查 Skill 至少需要：

```text
有边界的共享词汇
+ 可重复的候选检测器
+ 每条规则的误报说明
+ 方向性修复参考
+ 修改前的人工批准点
+ 最小改动与定向验证
+ 可持久化的有意例外
```

最重要的原则是：**检测器负责缩小注意力范围，代理负责解释上下文，人负责批准价值判断；工具输出是证据，不是结论。**

同时必须保留两条反制规则：

- taxonomy 会演进且文档可能不同步，因此研究、扫描结果和交接都应固定版本。
- 去掉默认套路只完成清理；最终结果仍需明确的产品声音、结构和视觉工艺。
